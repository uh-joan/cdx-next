A results page lets the user browse a collection and narrow it with filters. It composes three things you already have: a toolbar (search and a filter surface), the applied filters as removable chips, and a results region that is a region.

When to use it

Browsing or searching a collection — alerts, documents, drugs, trials — that the user narrows with filters. A short fixed list, or a single record (use a detail page), does not need it.

Anatomy

  • Toolbar — a search field and a filter surface. For many or hierarchical filters, put them behind a Filter button that opens a dialog (see ) or a panel (see ).
  • Applied filters — every active filter as a removable mat-chip-row, with a Clear all.
  • Results — a mat-table for modest lists, or the (AG Grid) for large datasets — wrapped in the four Page states.

Do

  • Derive the visible rows with computed() from filter signals.
  • Show every applied filter as a removable chip, with a Clear all.
  • Give the results region all four Page states; over-filtering to zero rows is the empty state.
  • Put many or hierarchical filters behind a Filter button.

Don't

  • Render an empty table on no matches.
  • Scatter filter controls with no single applied-state.
  • Hide which filters are active.
  • Keep a hand-synced copy of the filtered list.

State is derived, not stored

Keep the filter inputs as signals and derive the visible rows with computed(). The chips, the count and the table all read from the same derived value.

Empty is a first-class state

When filters match nothing, show an empty state with a way out — not a blank table.
