The app shell is the chrome every page sits in: the Helix header (Clarivate mark, product name, primary navigation, global actions), the routed content area, and the footer. Build it once in a layout component and let the router fill the content.

When to use it

The top-level layout of a product — every routed page renders inside it. A single embedded widget or a micro-frontend fragment the host already wraps does not need its own shell.

Anatomy

  • Header — header[hlx-header] with a hlx-header-product-name, the primary nav, and global actions in hlx-header-global. See the component.
  • Content — a <router-outlet/> where pages render.
  • Footer — footer[hlx-footer]. See the component.

Do

  • Assemble the shell once; pages render in the outlet.
  • Declare per-page chrome as typed route data.
  • Collapse the nav with HELIX_MEDIA, not innerWidth.
  • Make nav items real a[routerLink] with routerLinkActive.
  • Apply the theme classes on <body> so overlays inherit it.

Don't

  • Repeat the header/footer in each page.
  • Decide layout from window.innerWidth or a hardcoded width.
  • Use buttons or tabs as primary navigation.
  • Drill showFooter / showNav through component inputs.

Route-data-driven chrome

Per-page differences — does this page show the footer? which nav is active? — are declared on the route, typed, and read from the ActivatedRoute, not drilled through component inputs.

Responsive navigation

The primary nav shows inline at md and up, and collapses into a menu below md. Use the Helix breakpoint queries so the shell and the rest of the app agree on where that happens.
